# Modernize dependencies and harden the frontend across the four-service stack

The change bumps all four Node.js services to `node:26-bookworm`, upgrades the runtime dependencies (Express 5, node-cron 4, fluent-ffmpeg 2.1.3, cors 2.8.x), strips out bogus and unused npm entries (builtin names like `fs`/`path`, the dead `index.js`/`child-process`/`fs.promises` packages, and the never-wired `basic-auth`/`express-basic-auth`), and rewrites the peakfilegenerator image to install audiowaveform 1.10.2 from the BBC bookworm `.deb` instead of the dead `ubuntu:20.04` + `ppa:chris-needham` path. On top of that foundation it hardens the one user-facing write path (`POST /selection-export`) against path traversal and temp-file leaks, locks CORS to a safe same-origin default, moves the Express listen port behind `APP_PORT`, and flips nginx `autoindex off`. No authentication was added — the auth packages were removed, not wired up.

Watch for: stale committed `package-lock.json` files that still pin the old versions (confirmed) — harmless here because the Dockerfiles use `npm install`, which reconciles against `package.json`, but they no longer serve their purpose.

**Verdict**: APPROVED

## High-level view

The dependency and image modernization is the load-bearing part, and it is fully verified. All four images build and the running `security-update-*` images report Node v26.12.1, Express 5.3.0, cors 2.8.5, fluent-ffmpeg 2.1.3, node-cron 4.6.0, and audiowaveform v1.10.2 — the exact targets. node-cron 4 keeps the `cron.schedule(expr, fn)` signature the three cron services rely on, confirmed live.

The frontend hardening closes the two real holes in `selection-export` with defense in depth: a strict character whitelist on every path component rejects traversal attempts before any path is built, and a `path.resolve` containment check against the audio base dir is a second gate. The ffmpeg output now lands in `os.tmpdir()` and is cleaned up on success, ffmpeg error, and sendFile error alike, so no artifact leaks into the public audio directory.

CORS is now off unless `CORS_ORIGIN` is explicitly set, which is safe because the client calls its own origin. The listen port reads `APP_PORT` and defaults to 80, deliberately not consuming the host-facing `PORT` env, so the compose `${PORT}:80` mapping keeps working. nginx `autoindex off` is defense-in-depth only since the running container is Express-only.

The one blemish is the committed lockfiles: they still describe the pre-upgrade tree. Because every Dockerfile runs `npm install` rather than `npm ci`, the build regenerated the correct tree inside each image regardless, which the live version checks confirm. So it is a reproducibility/hygiene gap, not a correctness or requirement gap.

### Image and dependency modernization

All four Dockerfiles sit on `node:26-bookworm`; the recorder/cleaner/frontend bases predate this branch (already bookworm on `main`), and peakfilegenerator was rebased here. The original failure the user hit — `apt-get install ffmpeg` against the dead Debian buster repos — is resolved by the bookworm base, where the recorder's `apt-get update && apt-get install -y ffmpeg` resolves against live repos.

The peakfilegenerator rewrite installs `audiowaveform_1.10.2-1-12_amd64.deb` by path so apt pulls its runtime deps, and drops the `software-properties-common` + `add-apt-repository ppa:chris-needham/ppa` chain that no longer exists. The built image reports `AudioWaveform v1.10.2`.

Live inspection of the built images confirms the resolved tree matches the pins: Express 5.3.0 (`^5.1.0`), cors 2.8.5 (`^2.8.5`), fluent-ffmpeg 2.1.3 (`^2.1.3`), node-cron 4.6.0 (`^4.6.0`). node-cron 4 exposes `schedule` as a function and the three cron services call `cron.schedule(\`${minute} * * * *\`, fn)` — the signature is unchanged from v3, so no code change was needed.

### Path traversal and temp-file leak in selection-export

```
request params ─► whitelist regex (station_id, year, month, day, hour)
                     │ fail ─► 400 (before any path is built)
                     ▼
                 build file path ─► path.resolve(audioBaseDir, file)
                     │ escapes base ─► 400
                     ▼
                 fs.existsSync ─► 404 if missing
                     ▼
                 ffmpeg ─► os.tmpdir()/export-<ts>-<pid>.mp3
                     ├─ end  ─► sendFile ─► cleanupTempFile (even on send error)
                     └─ error ─► cleanupTempFile ─► 500
```

The whitelist (`station_id` `/^[A-Za-z0-9_-]+$/`, date parts anchored digit runs) runs before any path construction, so `../../etc` is rejected at the first gate; the `path.resolve` containment check against `audioBaseDir` is the backstop if the whitelist is ever loosened. `startTime`/`endTime` are coerced with `Number()` and required finite, non-negative, with `end > start` — the old `!startTime` truthiness check would have let `startTime=0` through and never bounded the range.

The temp artifact moved from `../audio/temp-<ts>.mp3` (inside the public, statically served directory) to `os.tmpdir()`, and `cleanupTempFile` runs on all three exits. The old code only unlinked in the sendFile callback, leaving the file behind whenever ffmpeg itself errored.

### CORS and listen port

CORS registers only when `CORS_ORIGIN` is set, parsed as a comma-separated allowlist; unset means no cross-origin middleware at all. The client fetches `${window.location.origin}/api/...`, so same-origin is unaffected and the previous blanket `cors()` (reflecting any origin) is gone.

The listen port reads `process.env.APP_PORT || 80`. The deliberate choice not to read the host-facing `PORT` (which compose injects as `PORT=${PORT}`, e.g. 9703) is what keeps the `${PORT}:80` mapping intact: the container still listens on 80, compose maps host 9703 → container 80. `APP_PORT` is an in-container override only.

### Build and smoke-test evidence

FEAT-002 records a full `docker compose build` + `up -d` smoke test on a temporary host port (19703, to avoid colliding with the user's still-running original stack on 9703), with all four containers reported `Up` and non-restarting and the expected startup lines (frontend `Server is running on port 80`; recorder/cleaner/peakfilegenerator `... is OK!`). The four `security-update-*` images are present on the host, and direct `docker run` checks reproduce the audiowaveform version and the installed dependency versions, corroborating the recorded evidence.
