# Mantine v8 → v9 upgrade plan (audiostreamlogger frontend)

Scope: upgrade `src/frontend` from Mantine **8.3.18** to the **9.7.x** line as ONE
coordinated bump across all `@mantine/*` packages. This supersedes Dependabot PRs
**#16** (`@mantine/dates` 8.3.18→9.x) and **#17** (`@mantine/hooks` 8.3.18→9.x),
which are CI-red because `@mantine/core@9` peer-requires `@mantine/hooks` at the
*exact same* 9.x version, so no single `@mantine` package can land in isolation.

Work happens in the worktree at
`/home/hoogden/Desktop/GIT/audiostreamlogger/.worktrees/mantine9` (branch `mantine9`),
NOT the main checkout. No backend / API / schema / docker / nginx change. The ONLY
dependency changes are the three `@mantine/*` bumps (plus a re-check of
`postcss-preset-mantine`, which turns out to need no change — see below).

Content was rephrased for compliance with licensing restrictions; facts verified
against the official [Mantine 8.x→9.x migration guide](https://mantine.dev/guides/8x-to-9x/),
the [color-schemes doc](https://mantine.dev/theming/color-schemes/), the
[dates getting-started doc](https://mantine.dev/dates/getting-started/) and the
npm-published 9.7.5 type definitions.

## Headline finding (breaking-change surface)

**This app's Mantine usage is almost entirely v9-clean already.** The only hard
code change v9 forces is **none** in the component props this app uses — the
risk-bearing surfaces (the custom `colorSchemeManager`, the dates
`DatePickerInput` string-value API, the CSS imports, `light-dark()` theming) are
all UNCHANGED between 8.3.18 and 9.7.x. The migration is therefore dominated by
the dependency bump + lockfile regen + a full typecheck/build/test pass, plus
TWO small optional/cosmetic items (light-variant CSS-var semantics; aligning the
test render helper's `defaultColorScheme`). Every PRESERVE invariant is expected
to hold with no behavioral edit.

> **Version note / deviation flag:** the task says "9.7.4 line". 9.7.4 is
> published, but the current latest is **9.7.5** and the official migration guide
> targets 9.7.5. The three packages MUST all be the same version (core's peer dep
> pins hooks/dates to core's exact version). Recommendation: pin all three to
> **9.7.5** (newest patch in the 9.7 line, matches the guide). If the workflow
> strictly requires 9.7.4, pin all three to 9.7.4 — just keep them identical.
> The plan below writes `9.7.5`; swap to `9.7.4` uniformly if required.

## (d) `color-scheme-manager.ts` — v9 interface: NO CHANGE

The `MantineColorSchemeManager` interface is **identical** in 9.7.5 and 8.3.18
(verified against the published 9.7.5 `types.d.ts`):

```ts
export interface MantineColorSchemeManager {
  get: (defaultValue: MantineColorScheme) => MantineColorScheme;
  set: (value: MantineColorScheme) => void;
  subscribe: (onUpdate: (colorScheme: MantineColorScheme) => void) => void;
  unsubscribe: () => void;
  clear: () => void;
}
```

The custom `systemColorSchemeManager()` returns `get: () => "auto"` (ignores the
`defaultValue` arg — fine, arg is optional to consume), and `set/subscribe/
unsubscribe/clear` as no-ops (`subscribe` ignores its `onUpdate` arg — fine). All
member signatures remain structurally assignable under 9.7.5. **No edit required.**
This directly preserves the invariant: app always follows the device, stale stored
scheme value ignored, no toggle. Live OS switching continues to be driven by
`MantineProvider`'s own `prefers-color-scheme` listener while the resolved value
stays `"auto"`.

## (e) dates / calendar migration — `src/App.tsx` `DatePickerInput`: NO CHANGE

`@mantine/dates` adopted **string values** (`YYYY-MM-DD`) back in the 7→8
migration, and v9 keeps that model. Verified against the 9.7.5 types and the v9
docs:
- `DatePickerInput` value type is `string | null` (docs usage:
  `useState<string | null>(null)`, `onChange={setValue}`). The app already does
  `value={date === "" ? null : date}` and `onChange={(value) => setDate(value ?? "")}`
  — string-based, **v9-compatible, no change**.
- `firstDayOfWeek?: DayOfWeek` (0–6; default **1 = Monday**). App passes
  `firstDayOfWeek={1}` — unchanged. (It's also the default, so Monday-first holds
  even if omitted.)
- Disabled-days: `excludeDate?: (date: DateStringValue) => boolean` where
  `DateStringValue` is the `YYYY-MM-DD` string. App passes
  `excludeDate={(value) => !existingDays.has(value)}` and `existingDays` is a
  `Set<string>` of `YYYY-MM-DD` — **type-matches v9 exactly, no change**. Days
  with a recording stay the only selectable days.

So the player calendar (Monday-first, days-with-recordings-only, string value fee
ding `parseDateParts`) needs **no edit**. This is the single most load-bearing
PRESERVE item and it is already on the v9 API.

> If the v9 typecheck surfaces any `DateValue`/`DateStringValue` naming nuance on
> the `excludeDate`/`onChange` callback params, the fix is a type-only annotation
> (annotate the param as `string`); no runtime/behavioral change. Treat as a
> typecheck-driven micro-fix, not a redesign.

## (g) Test files + `renderWithMantine` helper

The suites assert roles/behavior/DOM, not Mantine class names or colors, so the
v9 bump should not break them. No test needs a content rewrite. Two small,
OPTIONAL hygiene touches:

1. **`src/test/render-with-mantine.tsx` — align `defaultColorScheme`.** The helper
   wraps with `defaultColorScheme="dark"` while the real app uses `"auto"`. Under
   jsdom the `matchMedia` stub reports `matches: false`, so `"auto"` deterministic
   ally resolves to light. Changing the helper to `"auto"` (+ passing the real
   `colorSchemeManager={systemColorSchemeManager()}` to mirror the app) is a
   fidelity improvement, not a v9 requirement. **Optional**; if done, re-run the
   suite — role/text assertions are scheme-independent so they stay green. If it
   perturbs any snapshot-ish assertion, revert and keep `"dark"`.
2. **`src/test/setup.ts` — leave as-is.** The `matchMedia` + `ResizeObserver` jsdom
   stubs are exactly what v9 Mantine still needs under jsdom (FloatingIndicator
   controls observe resize; color-scheme logic calls matchMedia). No change.

Everything else in the test layer (`renderWithMantine` call sites, the
`MantineProvider` in `color-scheme-manager.test.tsx` with `defaultColorScheme="auto"`
+ custom manager) is already v9-correct.
